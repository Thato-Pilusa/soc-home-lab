# Investigation: Executable/DLL Dropped in a Folder Commonly Used by Malware

**Date:** 2026-09-20
**Endpoint:** win11-endpoint
**Severity:** rule.level 15 (critical range)

---

## Summary

The first alert generated by this lab was a critical-severity Sysmon detection triggered by Microsoft Edge's own update process, not an actual compromise. Documented here in full because the triage reasoning, not just the "false positive" conclusion, is the useful part: a legitimate detection rule fired correctly on a technique real malware also uses, and telling the two apart required actually looking at the evidence rather than trusting the severity label alone.

---

## Alert Details

| Field | Value |
|---|---|
| Rule ID | 92213 |
| Rule description | Executable file dropped in folder commonly used by malware |
| Rule level | 15 |
| Rule groups | sysmon, sysmon_eid11_detections, windows |
| MITRE ATT&CK ID | T1105 |
| MITRE tactic | Command and Control |
| MITRE technique | Ingress Tool Transfer |
| Sysmon Event ID | 11 (FileCreate) |
| Source process | `C:\Program Files (x86)\Microsoft\Edge\Application\msedge.exe` |
| Target file | `C:\Users\<user>\AppData\Local\Temp\msedge_chrome_Unpacker_BeginUnzipping<pid>_<id>\Microsoft.CognitiveServices.Speech.core.dll` |
| Occurrences | 2 (same pattern, different temp subfolder, ~4 minutes apart) |

---

## Why This Fired

Sysmon Event ID 11 (FileCreate) with the `sysmon_eid11_detections` ruleset flags files written into paths historically associated with malware staging, `%TEMP%` being one of the most common. Dropping an executable or DLL into a temp directory and then loading it is a well-known technique (MITRE T1105, Ingress Tool Transfer), used both by legitimate installers/updaters and by real malware delivering a second-stage payload. The detection rule is deliberately broad here because the alternative, ignoring temp-folder writes entirely, would miss genuine attacks.

---

## Triage

Working through this the way an analyst would, without assuming either verdict up front:

**What's suspicious about it, taken alone:**
- A DLL landing in `%TEMP%` is textbook staging behavior.
- The rule's own severity (15, critical range) and MITRE mapping (Command and Control / Ingress Tool Transfer) both point toward "attacker fetched a tool."

**What points the other way, once the full context is read:**
- The source process is `msedge.exe`, signed, in its expected install path (`Program Files (x86)\Microsoft\Edge\Application`), not a renamed or unusual binary.
- The target folder name itself, `msedge_chrome_Unpacker_BeginUnzipping`, is a distinctive, product-specific string. This isn't a generic temp folder name an attacker would use to blend in, it's Edge's own internal component-update mechanism unpacking a new module.
- The dropped file, `Microsoft.CognitiveServices.Speech.core.dll`, is a legitimate Microsoft library (used by Edge's built-in read-aloud/speech features), not an unsigned or unfamiliar binary.
- The event repeated on a second, differently-named temp subfolder a few minutes later, consistent with a multi-component update unpacking sequentially, not with a single payload drop.

**Verdict: benign.** This is Microsoft Edge's browser component updater extracting a new module during normal background updating. The detection rule did its job correctly, flagging a technique that genuinely warrants a look, it was the analysis, not the alert, that determined the outcome.

---

## What Would Make This Actually Malicious

Worth noting for future triage, since the same alert could look very different with different underlying evidence:
- Source process unsigned, running from an unusual path, or a renamed system binary
- Target filename mismatched with its actual content, or immediately executed after being written
- No plausible legitimate software mapping to the observed folder/file naming
- Follow-on activity from the dropped file (process creation, outbound network connections, registry persistence)

None of those indicators were present here.

---

## Lessons

- A rule's severity level reflects how dangerous the *technique* is, not a confirmed verdict on the specific event. Treating rule.level as "how worried should I be" instead of "how much attention does this deserve" is the wrong instinct.
- Process origin (signed, expected path, known vendor) is one of the fastest legitimate/malicious signals available, and it's usually the first thing worth checking.
- Filenames and folder names that are oddly specific (like `msedge_chrome_Unpacker_BeginUnzipping`) are often more informative than generic ones, a real attacker has no reason to use a string that specific and self-identifying.
